An asynchronous REST API for managing users, products, orders, payments, customers, and inventory activity. The project uses FastAPI, SQLAlchemy 2, PostgreSQL, Alembic, and JWT-based authentication, with Docker and Jenkins support for delivery to AWS ECS.

## Highlights

- JWT authentication with password hashing and role-aware access control
- Product catalog management with search, filtering, sorting, pagination, and stock visibility
- Order creation, retrieval, cancellation, and status transitions
- Customer profile creation and self-service updates
- Payment creation and payment status management
- Inventory transaction tracking for purchases, sales, returns, adjustments, and damaged stock
- Administrative dashboard, order visibility, restocking, low-stock reporting, and role management
- Interactive OpenAPI documentation generated by FastAPI
- Async database access through SQLAlchemy and `asyncpg`
- Versioned database schema managed through Alembic
- Production container image with a health check

## Architecture

The application follows a layered architecture:

```text
HTTP request
    ↓
API routes and dependencies
    ↓
Service layer (business rules)
    ↓
Repository layer (database queries)
    ↓
SQLAlchemy models and PostgreSQL
```

Route handlers are grouped by domain under `/api/v1`. Services contain business behavior, repositories isolate persistence concerns, and schemas define validated API input and output models.

## Run locally

### 1. Clone the repository

```bash
git clone https://github.com/manojkumargudge/order-inventory-system.git
cd order-inventory-system
```

### 2. Create a virtual environment

Windows PowerShell:

```powershell
py -3.14 -m venv .venv
.\.venv\Scripts\Activate.ps1
```

macOS/Linux:

```bash
python3.14 -m venv .venv
source .venv/bin/activate
```

### 3. Install dependencies

For application use:

```bash
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

For development, install the project with its optional development tools:

```bash
python -m pip install -e ".[dev]"
```

### 4. Configure the environment

Copy [`.env.example`](.env.example) to `.env` and update the values for your local PostgreSQL instance:

```powershell
Copy-Item .env.example .env
```

At minimum, set a unique `SECRET_KEY` and a valid `DATABASE_URL`. Keep `.env` out of version control.

### 5. Apply database migrations

```bash
alembic upgrade head
```

### 6. Start the development server

```bash
uvicorn src.main:app --reload
```

The API is available at <http://localhost:8000>.

## API reference

When the server is running, use:

| Resource | URL |
| --- | --- |
| Swagger UI | <http://localhost:8000/docs> |
| ReDoc | <http://localhost:8000/redoc> |
| OpenAPI JSON | <http://localhost:8000/openapi.json> |
| Health check | <http://localhost:8000/health> |

All versioned endpoints use the `/api/v1` prefix:

| Domain | Prefix | Description |
| --- | --- | --- |
| Authentication | `/api/v1/auth` | Registration, login, and current-user access |
| Products | `/api/v1/products` | Product catalog and stock visibility |
| Orders | `/api/v1/orders` | Create and manage customer orders |
| Customers | `/api/v1/customers` | Customer profile management |
| Payments | `/api/v1/payments` | Payment records and status changes |
| Inventory | `/api/v1/inventory` | Inventory transaction management |
| Administration | `/api/v1/admin` | Dashboard, restocking, order visibility, and roles |

Protected endpoints use the OAuth2 password flow. Include the access token returned by the login endpoint as a bearer token:

```http
Authorization: Bearer <access-token>
```

## Database migrations

Create a migration after changing SQLAlchemy models:

```bash
alembic revision --autogenerate -m "describe the schema change"
alembic upgrade head
```

Always review an autogenerated migration before applying it. Inspect the current database revision with:

```bash
alembic current
```

## Testing and code quality

Run the test suite:

```bash
pytest
```

Run the repository's static checks:

```bash
ruff check src/
mypy src/
```

Database-backed tests require a reachable PostgreSQL instance and a test `DATABASE_URL`. The Jenkins pipeline starts PostgreSQL 16 in Docker for its isolated test stage.

## Run with Docker

Build the production image:

```bash
docker build -t order-inventory-system:local .
```

Run the container with environment values supplied from a secure local file or deployment platform:

```bash
docker run --rm \
  --env-file .env \
  -p 8000:8000 \
  order-inventory-system:local
```

The image:

- Uses a multi-stage Python 3.14 build.
- Runs as a non-root `appuser`.
- Exposes port `8000`.
- Applies `alembic upgrade head` before starting Uvicorn.
- Checks `/health` through a Docker health check.

## CI/CD deployment

[`Jenkinsfile`](Jenkinsfile) defines the delivery pipeline for the `main` branch:

1. Ruff linting
2. mypy type checking
3. Pytest with PostgreSQL 16 in Docker
4. Docker image build
5. Push to Amazon ECR
6. ECS task definition rendering and service deployment

The pipeline is configured for AWS region `ap-south-1` and expects:

- Jenkins credentials with the ID `aws-credentials`
- An existing ECR repository
- An ECS cluster and service
- An ECS task definition family matching the pipeline configuration

Review [`ecs/task-definition.json`](ecs/task-definition.json) and [`ecs/render_task_def.py`](ecs/render_task_def.py) before using the deployment assets in another AWS account or environment. Secrets should be provided by AWS Secrets Manager or the deployment platform, never committed to source control.

## Configuration

The application loads settings from `.env` using [Pydantic Settings](https://docs.pydantic.dev/latest/concepts/pydantic_settings/). The supported values are documented in [`.env.example`](.env.example):

| Variable | Purpose |
| --- | --- |
| `APP_NAME` | Display name of the service |
| `APP_VERSION` | API/application version |
| `ENVIRONMENT` | Runtime environment name |
| `DEBUG` | Enables development debug behavior |
| `SECRET_KEY` | Secret used to sign JWTs |
| `ALGORITHM` | JWT signing algorithm |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | Access-token lifetime |
| `POSTGRES_HOST` | PostgreSQL hostname |
| `POSTGRES_PORT` | PostgreSQL port |
| `POSTGRES_DB` | PostgreSQL database name |
| `POSTGRES_USER` | PostgreSQL username |
| `POSTGRES_PASSWORD` | PostgreSQL password |
| `DATABASE_URL` | Async database connection URL |
| `BACKEND_CORS_ORIGINS` | Comma-separated allowed origins |
| `LOG_LEVEL` | Application log level |

## Security

- Use a long, random, environment-specific `SECRET_KEY`.
- Never commit `.env`, database credentials, cloud credentials, or access tokens.
- Use `DEBUG=False` outside local development.
- Store production secrets in a managed secret store such as AWS Secrets Manager.
- Review autogenerated migrations and deployment configuration before production use.
